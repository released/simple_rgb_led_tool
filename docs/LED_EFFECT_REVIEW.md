# `led_effect.c` Review And GUI-Friendly Pattern Architecture

This review covers the reference NUC1262 LLSI RGB LED sample's
`SampleCode/Template/led_effect.c` implementation. Line numbers refer to the
reviewed sample revision and may move in later BSP releases.

## Findings

1. `LLSIRGBBuffer` is hard-coded for a 6-LED debug path at lines 55-80. It is useful as a protocol check, but not suitable for GUI-generated patterns with variable LED count.

2. `setLED_ColorArrange()` at line 888 packs LED color into `LLSIDataBuffer` with no `DeviceNumber` bounds check. A generated pattern with more LEDs than `LED_NUM` can write outside the intended buffer mapping.

3. `setLED_ColorArrange()` uses `|=` at lines 952, 960, 961, 969, 970, and 978. This requires callers to clear the buffer before reusing a pixel location. Some effects clear every frame, but the dependency is implicit and easy for generated code to misuse.

4. RGB/GRB byte order is selected by a compile-time `#if 1` block at lines 944-1000. This should be a named configuration such as `RGB_ORDER_RGB` or `RGB_ORDER_GRB`, not an anonymous compile switch.

5. `colorsFull` is a 766-entry color table starting at line 89. It costs flash and makes the file difficult to maintain. Most of its behavior can be replaced by a compact wheel/HSV function.

6. Most effects are blocking loops with `delay_ms()`, for example `getRainbowCycle()` at lines 1491-1516 and `getTheaterChase()` at lines 1452-1488. This makes UART changes or future UI/live updates wait until the effect finishes.

7. `getFromAToB()` and `getAlternateColors()` divide by `steps` at lines 1149-1151 and 1357-1359 without guarding `steps == 0`.

8. `getPatternMove()` at lines 1294-1321 divides by `parts` and writes `index + i * indexStep` without checking that the computed LED index is below `LED_NUM`.

9. `getRGBSequence()` starts with `intensity = 0` and `sign = 0`, then decrements `intensity` at line 1394. On the first call it underflows to 255, which is probably unintended.

10. `uint8_t red , green, blue = 0;` at line 1417 initializes only `blue`. The wheel helper currently writes all three outputs, but this declaration style is fragile.

11. `StateMachine()` at lines 1627-1719 mixes state selection, effect execution, color-index updates, and blocking timing. This is hard for a GUI to generate because each new pattern becomes new C control flow.

## Recommended Architecture

Use three layers.

### 1. Low-Level RGB Driver

Responsibilities:

- Own the backend LED data buffer.
- Clear the buffer.
- Set one pixel with bounds check.
- Flush through LLSI, SPI, SPI + PDMA, or GPIO bit-bang.
- Hide RGB/GRB packing details behind named configuration.

Generated driver API, with backend-specific prefix:

```c
void <BACKEND>_LED_PATTERN_DRV_Init(void);
void <BACKEND>_LED_PATTERN_DRV_Clear(void);
void <BACKEND>_LED_PATTERN_DRV_SetPixel(uint8_t index, uint8_t red, uint8_t green, uint8_t blue);
void <BACKEND>_LED_PATTERN_DRV_Show(void);
void <BACKEND>_LED_PATTERN_DRV_DelayMs(uint16_t ms);
```

The GPIO backend is generated inside the driver because the MS51 GPIO samples do not expose a standard peripheral transfer API. Its pin write, pin init, NOP, and interrupt critical-section macros are intentionally editable in `gpio_led_pattern_drv.h`.

### 2. Pattern Player

Responsibilities:

- Render a frame table generated by the GUI.
- Provide blocking `play_once()` for demos.
- Provide non-blocking `step()` for production firmware.

Suggested frame data:

```c
typedef struct
{
    uint8_t r;
    uint8_t g;
    uint8_t b;
} llsi_led_pattern_color_t;

typedef struct
{
    uint16_t duration_ms;
    llsi_led_pattern_color_t led[RGB_PATTERN_LED_COUNT];
} llsi_led_pattern_frame_t;
```

### 3. Generated Pattern Data

Responsibilities:

- Contain only const frames and small wrapper functions.
- Avoid custom loops per effect.
- Let the GUI produce repeatable output.

Generated pattern example:

```c
static const llsi_led_pattern_frame_t g_rgb_pattern[RGB_PATTERN_FRAME_COUNT] =
{
    { 100u, {
        { 0xFFu, 0x00u, 0x00u },
        { 0x00u, 0xFFu, 0x00u }
    } }
};
```

## Why This Fits GUI Generation

- The GUI only needs to create frames and colors, not firmware control flow.
- LED count is explicit in the generated data.
- Preview and MCU output use the same data model.
- Presets can be generated as data tables, then users can edit individual frames.
- MCU code review becomes focused on renderer safety instead of every effect function.

## Migration Plan

1. Add the generated `<backend>_led_pattern_drv.*` and `<backend>_led_pattern_player.*` files to the BSP project.
2. Keep the target BSP transfer hooks, such as `LLSI_PDMA_Transfer()`, SPI write, SPI PDMA transfer, `delay()`, and `delay_ms()`. The generated driver header defines `LED_NUM` from the GUI LED count and derives `LED_DATA_LEN`; if the BSP must own these macros, define them before including the generated driver header.
3. Call `<symbol>_play_once()` from `StateMachine()` as one new demo state.
4. Use `<symbol>_step()` from a timer state machine if live command updates are required.
5. Add a separate generated prefix later for PWM if needed.
